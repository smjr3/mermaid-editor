# UI language

The editor's interface strings live in one catalogue and are looked up through a
typed accessor. There is no i18n framework.

## Why not a framework

Paraglide, the usual SvelteKit choice, wants a build plugin and — in its
SvelteKit integration — ownership of locale routing, so the locale lives in the
URL. This fork ships a single locale and builds a static site served from a fixed
subpath, so that machinery buys nothing and constrains the build and URL design.

The one thing a framework would genuinely buy — UI strings in one place instead
of scattered across components — is what `src/lib/i18n/messages.ts` provides on
its own, in about sixty lines with no dependency.

## Layout

| Path                       | Role                                                                        |
| -------------------------- | --------------------------------------------------------------------------- |
| `src/lib/i18n/messages.ts` | The catalogue: `en` holds upstream's original wording, `ja` the translation |
| `src/lib/i18n/index.ts`    | `t(key)` and the resolved `locale`                                          |
| `MERMAID_LOCALE`           | Build-time locale, `ja` by default; `en` restores upstream's wording        |

Keys are typed off the English catalogue, so a typo or a message deleted from the
catalogue is a compile error rather than a blank label at runtime. `t()` falls
back to English if a key is ever missing from another locale.

Both catalogues ship in the bundle. The locale is fixed at build time but read
through a runtime object lookup, so the unused one is not tree-shaken — a few
hundred bytes for the current key count, not worth complicating the accessor to
avoid.

## Adding or changing a string

1. Add the key to **both** `en` and `ja` in `messages.ts`, keeping each object
   alphabetical — eslint's `sort-keys` rule enforces that on objects this size.
2. Use `t('your.key')` in the component.
3. Run `pnpm check`. A key present in `ja` but missing from `en` is a type error.

## Migration status

The editor chrome a user works in is done — 57 keys. Migrated: `PanZoomToolbar`,
`SyncRoughToolbar`, `VersionSecurityToolbar`, `Navbar`, `routes/+error.svelte`,
`Preset`, `Actions`, `History/History`, `Editor`, `routes/(app)/edit/+page.svelte`
(the Code/Config tabs and the History toggle) and `Share`'s subtitle and embed
preview.

Not yet migrated: `MainMenu`'s entries, the rest of `Share`, `Privacy`,
`DiagramDocumentationButton`, `AIPromptPopup`,
`migration/EditorChooserModal`, `routes/embed/+page.svelte`, and the
notification strings in `src/lib/util/`. Several sit behind disabled feature
flags and never render.

Two interpolated titles are worth calling out. The theme toggle was
`title="Switch to {…} theme"`; rather than teach `t()` interpolation for one
string, it became two keys, `toolbar.switchToLight` and `toolbar.switchToDark`.
`DiagramDocumentationButton` builds its title from the diagram type
(`View documentation for flowchart diagram`) and still needs the same treatment
or a real interpolation helper — it is the last English string visible in the
default chrome.

## Keeping the e2e suite language-independent

The suite reaches for UI text far more than for `data-testid`, so translating a
string breaks whatever selector names it. Two fixes are in use, chosen per case:

**A `data-testid` where the element has no useful accessible name.** `Card`
gained a `testID` prop, and `TID` gained `actionsCard` and `sampleDiagramsCard`,
so `toggleActions()` and `toggleSampleDiagrams()` click by id rather than by
title.

**The catalogue itself where the selector is an accessible name.** `getByRole`
selectors read better naming the thing they mean, so `tests/test.ts` exports its
own `t()` and the specs assert against it:

```ts
await page.getByRole('tab', { name: t('history.tabTimeline') }).click();
```

That `t()` is a few lines in `tests/test.ts` rather than a re-export of
`$/i18n`, and the reason is worth knowing before trying the tidier-looking
version: `$/i18n` imports `src/lib/util/env.ts`, which reads `import.meta.env`.
Playwright runs the specs in plain Node, where that does not exist, so importing
the app's accessor makes every spec in the file fail to load. `messages.ts` is
pure data and imports fine; the test-side `t()` reads `process.env.MERMAID_LOCALE`
to pick the same locale the build under test uses.
